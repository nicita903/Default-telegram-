# Audible call ringing correction

## Evidence and cause

The original eight call WAVs exist and were already packaged. Original SoundPool decoding returned
status 0. The prior outgoing implementation used USAGE_VOICE_COMMUNICATION_SIGNALLING (DTMF),
checked VOICE_CALL volume instead, and suppressed all playback outside communication mode.
These are different Android audio policies; audio mode is not a safe pre-answer playback gate.

The first instrumented physical test also exposed an incoming focus collision: Telecom registered
the call and started its foreground service, but a separate ringtone focus request returned 0
(denied). A subsequent request briefly returned 1, then received -2 and stopped before ringing.
The user reported no audible ringback in that first test. SoundPool stream acceptance alone did
not demonstrate audible output. No success is inferred from those logs.

## Corrected ownership

`CallSoundController` remains the single owner, observed by the existing foreground call service.
It now uses three suitable mechanisms within that controller: one looped Ringtone for incoming,
one MediaPlayer at a time for Waiting/Ringback/Connecting, and the existing SoundPool for short
initiation/connected/busy/end/failure cues. No Compose screen owns audio.

Incoming uses the existing channel's configured sound or the system ringtone, ringtone attributes,
and ring volume. The visible CallStyle notification uses a separate high-importance, soundless display channel
and has no INSISTENT sound loop, so it cannot double-play. Incoming notifications deliberately
omit FLAG_SILENT/group suppression, which otherwise can prevent full-screen display. Telecom remains the audio-focus authority; the app does not
make a competing ringtone focus request. Silent/DND, channel importance, notification permission,
channel-silent URI and channel vibration preference are checked. Priority-DND currently suppresses
app ringing conservatively rather than bypassing contact-specific restrictions.

Incoming vibration starts independently of audible playback using the channel pattern (or a
350ms-on/650ms-off default), ringtone vibration attributes and the existing VIBRATE permission.
It is never used as a continuous outgoing-call vibration. Answer, decline, cancel, timeout, failure
and service cleanup cancel it. Answer latches ringing off before communication setup; a volatile
incoming-intent check prevents a slow resource load from starting a ringtone after termination.

Outgoing loops use the actual WAV resources through MediaPlayer with voice-communication/speech
attributes and voice-call volume. Telecom alone selects earpiece/speaker/headset endpoints.
They do not use a ringtone, DTMF stream, force speaker, change AudioManager mode or create another
focus controller. Async prepare completes only for the current cue/session; actual `isPlaying`,
loop state, decoder errors and routed-device callbacks are logged. State changes stop/release the
old loop before any next cue. All resources are call-scoped, including interruption listeners.

Real TDLib `is_created` selects Waiting; `is_received` selects remote Ringing. Native Established
alone selects Active and stops setup loops. The native engine/JNI, encryption, verification emojis,
UI, mute/speaker controls, proximity and haptics are unchanged by this correction.

## Assets and diagnostics

Original CC0 assets: call_start, call_waiting, call_ringback, call_connecting, call_connected,
call_busy, call_ended, call_failed under `app/src/main/res/raw/`, generated by the existing script.
No new sample or external recording is needed. SoundPool is retained only for short effects;
MediaPlayer now provides observable playback and routing for the loopable assets.

`adb logcat -s DefaultCallAudio DefaultTelecom DefaultVoiceCall` reports:
INCOMING_CALL_RECEIVED, RINGTONE_START_REQUESTED, RINGTONE_PLAYING, RINGTONE_STOPPED,
RINGTONE_VIBRATION_STARTED/STOPPED, OUTGOING_CALL_STARTED, REMOTE_RINGING_DETECTED,
RINGBACK_START_REQUESTED, RINGBACK_PLAYING, RINGBACK_STOPPED, CALL_AUDIO_ROUTE,
CALL_AUDIO_FOCUS and CALL_ENDED. Suppression reasons and fixed exception class/error numbers
are included; no contact identity, phone numbers, ringtone URIs or authentication data are logged.
Ringtone and MediaPlayer `reportedPlaying=true` is a player report, not proof of physical audibility.

## Files changed for this correction

- `calling/CallSoundController.kt`: actual incoming Ringtone/vibration, observable outgoing loops,
  correct stream policy, no competing focus request, lifecycle guards and diagnostics.
- `calling/TelegramCallPlatform.kt`: soundless visual notification channel, full-screen presentation,
  immediate incoming stop hook and safe presentation diagnostics.
- `MainActivity.kt`: fixed-field diagnostics for validated call-window delivery (no security bypass).
- `calling/TelegramVoiceCalls.kt`: fixed event diagnostics at real TDLib/start/termination points.
- `calling/CallDiagnostics.kt`: sanitized audio diagnostic helper.
- This report and links in existing calling documentation.

Calling paths above are under `app/src/main/java/com/vector/messenger/`.

## Verification

Initial instrumented build: assembleDebug passed in 32s, installed with `adb install -r` preserving
app data. Real incoming and outgoing attempts reached Telecom registration. Incoming playback was
blocked by focus denial; the user reported silent outgoing feedback. These tests failed and led
to the corrective changes above.

Corrective build: assembleDebug passed in 17s and was installed with data preserved. All eight
packaged WAVs contain nonzero PCM samples; native library SHA-256 matches the reviewed manifest.
On the corrective APK, the user confirmed: "Ringtone and vibration work and stop" after incoming
ringing and decline. Logs show reportedPlaying=true/looping=true, vibration start, then both
vibration and ringtone stopped with reportedPlaying=false. Three successive incoming sessions
registered and cleaned up without overlapping owners. The user subsequently confirmed outgoing ringback was audible, stopped on answer, and two-way
speech worked. A connected incoming session also produced native Established in the trace;
its connecting MediaPlayer reported isPlaying=true, routed device 1 (earpiece), and stopped on
Established. Ringing and vibration stopped on Answer before communication media setup.
No unrelated tests or native rebuild ran. Physical audibility, cancellation and two-way speech
must be recorded explicitly, not inferred from compilation.

## Lock-screen and proximity follow-up

The connected phone initially denied full-screen-intent access. The user enabled it through the
supported Android settings page. A remaining silent-notification flag could suppress full-screen
presentation, so incoming visual alerts now use `telegram_incoming_call_display_v1`: importance
HIGH, sound null, vibration disabled, and no silent/group suppression flag. The prior RING channel
retains the user's ringtone/vibration preference; the controller remains the sole audio owner.
The display channel's blocked state is also honored. Keyguard is not dismissed or bypassed.

The final presentation build passed assembleDebug in 13s and was installed with data preserved.
Device trace: fullScreenAllowed=true, locked=true, interactive=false, then CALL_WINDOW_OPEN_REQUESTED
and CALL_WINDOW_RESOLVED valid=true. The user confirmed the call screen appeared without unlocking,
Answer worked, and proximity still worked. Prior connected-call proximity trace showed Established,
PROXIMITY_LOCK_ACQUIRED=true, repeated near/far transitions, then PROXIMITY_LOCK_RELEASED=true.
The proximity controller itself was not changed; it correctly activates for an established earpiece
call, not unanswered ringing. The tested Telecom/native call reached Established without registration
failure. Repeated real incoming sessions stopped/released ringtone and vibration on termination.

Physical results on the connected Samsung SM-S9310 (Android API 36), reported by the user and
cross-checked against fixed diagnostics: incoming audible ringtone/vibration and decline cleanup;
outgoing ringback, stop-on-answer and two-way speech (user confirmation); answered incoming native
Established; earpiece near/far display behavior and wake-lock cleanup; locked-screen call-window
presentation with full-screen permission enabled. Local sanitized evidence is in the ignored
`ringing-device-verification.log`.

Still not comprehensively tested: process death/FCM restoration, timeout, custom ringtone failure,
all DND/silent/vibrate policies, Bluetooth/wired handover, other OEMs/Android releases and extended
repeated-call stress. No success is claimed for those cases.
