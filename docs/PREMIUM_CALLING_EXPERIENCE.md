# Premium calling experience

## Existing architecture preserved

This refines the existing TelegramVoiceCalls state flow, AndroidX Core-Telecom endpoint controller,
notification-owned incoming ringtone, foreground call service, SoundPool, and calling composables.
There is no second call session, ringtone player, audio focus controller, or native engine.
JNI, tgcalls/WebRTC, encryption parameters, four-emoji verification, authentication, session lifecycle,
message/media systems, global navigation and theme settings are unchanged. The service-owned
proximity controller is unchanged, including its actual communication-device observation.

## State and sound behavior

- Calling: existing Requesting state and one initiation cue once registered communication audio is ready.
- Waiting: actual TDLib `callStatePending.is_created` without `is_received`; new soft looping `call_waiting.wav`.
- Ringing: actual `is_received`; existing ringback cadence. No timer or animation invents a ringing event.
- Connecting: actual key exchange / initial media setup; the existing connecting cue replaces waiting/ringback.
- Connected: only native Established sets Active and the timer origin. Existing one-shot confirmation cue;
  recovery does not repeat it. All setup loops stop.
- Ended/failed/busy or declined: existing deduplicated terminal sounds and real errors are preserved.

The eight original CC0 WAVs are generated by `scripts/Generate-CallSounds.py`; the new waiting asset
is 1.8 seconds of mono 24 kHz PCM containing a soft pulse and silence. SoundPool still has one stream,
loads on its worker, and is released after the bounded terminal tail. Existing effects, volume,
silent mode, DND, communication-mode and teardown gates remain active. Policy suppression is not
replaced with another player or an independently acquired audio focus session.

## Incoming ringtone and vibration

The existing `telegram_incoming_calls_v1` channel remains the sole incoming ringtone/vibration owner.
It uses its user-configured sound or the system ringtone and retains Android's importance, silent,
DND and vibration controls. The initial real incoming notification is now explicitly alerting;
subsequent caller/photo updates use only-alert-once. Outgoing/ongoing notifications are explicitly
silent, preventing a custom ongoing channel from becoming a second call sound. Answer posts the
silent ongoing CallStyle notification before enabling communication audio; cancellation, decline,
timeout and termination use existing notification cancellation. No foreground notification is
cancelled/recreated merely to switch incoming/ongoing styles. The normal VIBRATE manifest permission
supports notification vibration; no new runtime permission or custom vibration loop is introduced.

## Setup controls

Mute and Speaker are now visible and enabled for Calling, Waiting, Ringing and Connecting as well
as Active/Reconnecting. Their state belongs to the existing controller, not a composable.

Mute before native creation records the requested user state. At native creation that effective
user/system mute is applied before signaling is drained. Native acceptance is checked, duplicate
commands are suppressed, and a failed application of startup mute terminates setup instead of
silently connecting unmuted. A later rejected toggle retains the prior selected state and reports
an error. Android system mute still wins over user unmute. This checks command acceptance, not
proof that a remote participant heard silence; physical verification remains required.

Speaker requests made before Telecom registration or endpoint discovery are queued in the existing
platform controller. Only real available endpoints are requested. Selection is retained by Telecom
across native establishment; the speaker icon follows the actual endpoint report, not request
intent. Switching off restores an available prior private route or the wired/Bluetooth/earpiece
preference. Explicit headset selections are retained. Rejected requests leave the reported route
unchanged and show an error. No fake earpiece is added for speaker-only hardware. Queued intents
are cleared during existing call cleanup and cannot carry into a replacement call.

## UI, motion and haptics

- Existing centered avatar/name and encryption emojis remain; 56dp Mute/Speaker, 64dp End and incoming
  Answer/Decline controls. Incoming Answer uses the theme's online-green surface; Decline remains red.
- Incoming avatar scale breathes from 1 to 1.018 at normal intensity; no glow or rings.
- Native establishment triggers one 1.015 avatar pulse, remembered per connection across screen
  recomposition/minimization. Background or terminal calls do not replay it.
- Three small dots animate opacity only in setup. The fixed slot prevents vertical status jumps.
- Status crossfades in 180ms; control icons in 150ms; selection in 170ms. Incoming-to-calling controls
  fade and resize in 220ms. Call session and native engine ownership do not depend on these branches.
- Press scale is 0.97 with tween easing and no spring overshoot.
- App reduced motion and system animator policy are preserved. Continuous effects stop in the
  background or when minimized; dots stay static under reduced motion.
- Mute, Speaker, End and Decline taps use Android View CLOCK_TICK; Answer uses CONFIRM on API 30+
  with a virtual-key fallback. No haptic runs from animation frames or recomposition. The app haptic
  switch, Android touch-feedback setting, ringer mode and DND policy gate feedback. No force flags
  or independent Vibrator are used. Feedback failure never prevents the actual call action.
- Buttons expose descriptions and selected/state semantics; real status changes use a polite live
  region, while the timer is not announced every second.

## Verification and device checklist

The user selected **leave a device-test checklist**. No APK installation, outgoing/incoming call,
answer, mute, speaker, audible sound, haptic, two-way media or proximity test is claimed for this update.
Read-only inspection of the connected phone showed the incoming channel at importance 4, system
ringtone URI, vibration enabled and DND bypass disabled. This is configuration evidence only.
The filtered call log contained no current native-establishment/Telecom trace to validate.

First install the built APK and use a consenting Telegram peer. Watch
`adb logcat -s DefaultTelecom DefaultVoiceCall DefaultProximity`. Require `addCall.scopeReady`,
`startForeground.complete`, EngineInitialized and native Established. If "Android could not register
this call" occurs, stop and capture the sanitized operation/code/exception before interpreting
any audio or motion. Existing visible registration errors remain; no animation declares Active.

| Check | Required physical evidence |
| --- | --- |
| A - Outgoing | Calling/Waiting/Ringing follow real TDLib updates; initiation then appropriate waiting/ringback; Mute/Speaker/End visible. No incoming ringtone on outgoing calls. |
| B - Setup mute | Mute before the peer answers, then establish speech: selection persists and peer hears silence. Unmute restores speech. Repeat rapid toggles and minimize/return. |
| C - Setup speaker | Select Speaker before endpoints are ready and while ringing; connect and verify actual loudspeaker output. Switch back; verify earpiece or explicitly selected headset and proximity behavior. |
| D - Incoming | Real ringtone and OS vibration exactly once, including background/locked screen and caller-photo updates. Test custom/default ringtone, silent/vibrate/DND, volume zero and disabled channel vibration. |
| E - Answer | Ringtone/vibration stop before communication audio; same call transitions smoothly; green Answer invokes the real call; two-way audio and emoji verification remain. |
| F - Hangup/failure | Local/remote end, decline, cancellation, timeout and platform failure stop loops/vibration and release microphone, focus, Telecom and proximity. Real error stays visible. |
| G - Repeated calls | Repeat incoming/outgoing calls with setup mute/speaker; no inherited mute intent, queued route, duplicate sound, repeated confirmation or native session. |

Also check Bluetooth/wired insertion/removal, explicit headset selection, tablets without an
 earpiece, near-ear remote hangup, Android reduced motion, app haptics off, system touch haptics off,
TalkBack, large fonts, short landscape windows, Console, Aurora Glass and AMOLED.

## Build result

`./gradlew.bat :app:assembleDebug` succeeded on the first run in 1m 18s. All eight call WAVs,
including the verified non-silent waiting cue, are packaged. The packaged arm64 calling library
matches the existing reviewed SHA-256. No tgcalls/WebRTC build or unrelated test suite ran.
The APK was not installed, and physical call checks remain unperformed at the user's request.

- `calling/TelegramVoiceCalls.kt`: Waiting state, pending/deduplicated native mute and queued Speaker intent.
- `calling/TelegramCallPlatform.kt`: queued setup route requests, real-route failure handling, first-alert

- `app/src/main/AndroidManifest.xml`: normal VIBRATE permission for incoming notification vibration.

- This report and the calling-status documentation links.
